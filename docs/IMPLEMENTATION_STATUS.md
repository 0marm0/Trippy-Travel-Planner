## Works without credentials

Generic workspaces start empty, preserve the traveler's destinations/dates and do not inherit sample bookings or geography. Day activities carry manual local times, durations and notes; feasibility checks flag overlaps, midnight spill and destination/locked-anchor conflicts. Route alternatives preserve supplied city orders. Optional whole-night allocations derive dates, check minimum/maximum nights and fixed anchors, then preview day destinations before acceptance. Existing activity and booking dates are preserved; ranking, schedules and inventory are not inferred. The versioned reading model is [`src/lib/planning-view.ts`](../src/lib/planning-view.ts). Booking record changes require preview and acceptance with the canonical states `recommended`, `quoted`, `held`, `confirmed`, `missing`, `conflict`.

The generic **Trip tools → Detailed cities & days** preview uses [`canonical-atlas.ts`](../src/lib/canonical-atlas.ts) and the mounted `CanonicalTripWorkspace` in [`trip-workspace.tsx`](../src/components/trip-workspace.tsx). It reuses the existing city rail, activity grid, day column and accessible activity inspector. A validated detached workspace retains every supported sidecar and exact booking state; absent coordinates, photos, priorities, stay dates and prices are not replaced with sample assumptions. State is scoped to the trip/date/party identity, without separate preview persistence. Activity CRUD, day moves, destination names/manual pins and attributed public photographs are editable with the manual workspace’s undo history. Booking edits still use the existing reviewed editor. The sample remains a specialized compatibility surface and has not become a fully generic editable data pack.

Browser saving is explicit and isolates records by trip ID, dates and destinations. Resume/forget controls manage the saved workspace; unsaved preview records remain in memory. Optional workspace `itemEvidence`, `routeAllocations`, `researchEvidence`, `quoteEvidence` and `budgetQuoteIds` are validated and retained in explicit browser saves, account saves/loads and itinerary exports. Standalone research/quote storage and JSON exports remain available; they are recorded evidence, not implicit booking authority. Item receipts can record source/time/unknowns and become `reviewRequired` when their supported entity changes. Itinerary undo/redo preserves the separately edited research and quote state. Browser storage is device-local and accessible to other users of that browser; it is not encrypted cloud sync.

The device trip library indexes up to 40 explicitly saved validated workspaces, with the last saved legacy workspace also discoverable. Listing is read-only; preview and Open revalidate records and opening does not save or upload. An indexing failure does not erase a successfully saved plan. Complete-workspace JSON can be downloaded, validated, previewed and explicitly accepted into memory from `/plan`; states are retained as supplied, not independently verified. This is not a general migration engine or unified atlas/account/room registry. See [`workspace-library.ts`](../src/lib/workspace-library.ts) and [`workspace-library.test.mjs`](../tests/workspace-library.test.mjs).

`trip:init`, `trip:validate` and `schema:check` share normalized validation. Generic planning JSON and itinerary sidecars retain editable records; visual HTML and compact travel/transit/hotel HTML/PDF provide reading copies. Atlas visual/light/dark exports and CSV remain available. Both workspaces open Export studio for scope/layout/theme review, a titled sandboxed HTML preview, actual HTML byte budget and photo-candidate inventory. Linked preview images require explicit opt-in; PDF server/network limits remain visible. [Formats, privacy and offline limits](EXPORTS.md).

The generic workspace can prepare a validated activity-board JSON handoff: review it in `/collaborate` before creating a room. Only cities, coordinates, activities and day assignments transfer. This is explicit file interchange, not bidirectional synchronization with a live room or the sample atlas.

## Optional research and imports

Implemented adapters include SerpApi cash flights/hotels/places/web, Seats.aero cached award flights, separately eligible commercial Live Search, Rooms.aero and eligible Booking.com Demand. Provider tests use mocks and zero-credential degradation. Host travel connectors remain independently installed and authorized agent tools; they do not become website credentials. Rail/car/coach/ferry/operator gaps use manual or authorized source research.

Connections now exposes editable cash adults/cabin/currency, explicit cash-stay dates/adults/rooms/currency and award seats/program. Available profile facts initialize the request; missing fields remain unknown. Sort reorders returned cash/time evidence with disclosed missing-value/currency/unit limits; editing controls or capability cancels stale requests. Unsupported award-cabin/guest-room and child-pricing constraints are disclosed rather than simulated. See [`provider-search-controls.ts`](../src/lib/provider-search-controls.ts) and [`integration-center.tsx`](../src/components/integration-center.tsx).

The bounded cash matrix prepares a maximum 24-query exact airport/date scope before an explicit run, uses two workers without retries/pagination, supports cancellation and rejects stale generations. Found, searched-empty, failed, locked, unconfigured, cancelled and not-searched scope remain distinct. The optional reviewed receipt replaces one cash coverage row; it does not create quotes or bookings. Provider check/cache time is separate from the local receipt time. Child pricing, award queries, through tickets/open jaws, hotels and other transport modes are not covered. See [`research-matrix.ts`](../src/lib/research-matrix.ts) and [`research-matrix.test.mjs`](../tests/research-matrix.test.mjs).

Private Gmail is a read-only candidate preview, with consent before reading and separate approval before any import/state change. It has no durable approve/reject ledger. No local verification used a real mailbox, provider key or private confirmation. [Integration coverage](INTEGRATIONS.md).

## Collaboration and account persistence

Rooms require explicit enablement and persistent Node/SQLite or user-owned Postgres; remote/production creation requires a private creation code. Owners manage dates/cities/invitations, rotate their owner link and delete rooms; editors modify activities/days; viewers read. New invitations expire, revocation and deletion deny subsequent server access, and stale management/writes fail closed. Optional activity/day suggestions remain separate pending records. General writes append pending proposals without rewriting existing ones; only an owner can apply/reject in a current-revision transaction. Applied/rejected receipts remain immutable, and legacy boards without suggestions remain valid. Field/entity/day/suggestion reconciliation requires explicit choices and validates references; another revision pauses application. Consent-based recovery retains only a validated board and base revision, with capabilities and unfinished forms excluded. [Live contract](LIVE_COLLABORATION.md).

Pending suggestions also support server-managed support/concern/neutral choices and safe comments. The server derives an owner/editor access pseudonym from the resolved capability row, not from a client author field; one access has one current choice per proposal. A shared invitation can represent several people, and a rotated/new access is distinct. These are not verified person identities or personal must-do lists. Comments are capped at 500 safe characters, 200 records per room; votes at 1,000 records, with a 512 KiB interaction-write state limit. General PATCH cannot forge/edit/drop discussion history; only authenticated current-revision actions can update a vote or append a comment. Viewers read; expired/revoked access cannot write. New-room creation rejects imported interaction history. Reconciliation always retains latest server discussion, and unfinished comment text stays only in the current tab, including when a conflict interrupts posting. Posted discussion remains with resolved proposals until room deletion; no standalone comment deletion, notifications, presence or board audit history is implemented. See [`collaboration-interactions.test.mjs`](../tests/collaboration-interactions.test.mjs).

Optional accounts use database-checked sessions, AES-256-GCM plan encryption bound to owner/plan IDs, tenant-qualified queries and revision-conditional updates/deletes. There is a 20-plan limit per account. Account deletion requires the current password and removes server plans/authentication/session records; exports, local copies and backups remain outside that deletion. Password recovery has an injectable transport tested with a mock, but no real transport or recovery UI is wired. Authentication metadata is separate from encrypted trip content. [Configuration and custody](PRIVATE_ACCOUNTS.md).

SQLite tests exercise restart durability and access restrictions with synthetic records. Postgres adapters are implemented but no user-owned remote database was provisioned or tested. Hosted operation, request throttling, enrollment, backups and retention remain operator responsibilities.

## Remaining verification and product gaps

- Optional item receipts are available but do not populate themselves or prove every fact is current; review-required receipts and missing sources remain visible gaps.
- Quote comparisons require like-for-like human review; transfers, taxes, service schedules, opening hours and bookability must be reverified.
- Generic workspaces do not replicate every specialized atlas catalogue, city photograph, hotel map or quote-selection feature.
- No automatic booking, points transfer, invitation/email sending or calendar mutation; no presence, room audit history, end-to-end encryption or recovery of a lost room-owner capability.
- Final integrated command/browser outcomes belong in [the current release receipts](RELEASE_REPORT.md); focused source tests do not replace independent accessibility/public-release review or authorized real-provider/hosted-storage validation.

Repository publication and deployment require explicit authorization. The existing demo may lag this source and was not redeployed by these changes.

## New local planning tools

**Route & map → Compare the whole journey** previews up to six city-order/night proposals and retains manually recorded gateway/ticket/protection/leg scenarios linked to existing quotes. Cost comparisons reuse party/currency/program math and block equivalent winners when scope or required facts are missing; no sourced schedule feasibility or automatic inventory optimization is implied. **Trip tools → Scenarios & snapshots** offers reviewed identity-separated copies, explicit booking-copy policy and named device snapshots with a readable restore diff and current-copy disposition. **Friends & shared edits** performs reviewed three-way supported board edits against a downloaded base; unsupported fields or city/date identities remain blocked and private bookings/research remain separate.

Display controls support liquid glass/solid surfaces, compact/comfortable spacing and reduced motion. Rooms optionally show 30-second access-capability leases and authenticated bounded revision notices, preserving four-second polling and conflict review. Export studio supports inclusive selected reading dates while preserving original overlapping booking terms and explicit trip-wide context. Hosted Postgres, provider access, public release and independent accessibility acceptance remain separate.


## Preparation, booking metadata and room history

The generic workspace supports optional versioned `bookingPlans` and `preparation` records. **Stays & transport** links existing bookings to reviewed stay photos/pins or transport endpoints and entered elapsed/transfer minutes. It preserves reservation states, dates and explicit unknowns, with recorded comparisons shown only as possible context. Removing metadata is reviewed separately from changing a booking type.

**Trip tools → Tasks, packing & alternatives** stores manual tasks, packing roles, completion and optional date/city/activity references. Existing same-city activities can form rainy-day, low-energy, accessibility-review or other pairs. An explicit stale-checked preview swaps date/start slots, conserves both activities and marks affected evidence for review. No automated weather, suitability verification, notifications or verified assignee identity is provided. Complete-workspace JSON/device/account storage retains these fields; linked records must be repaired before deletion.

Enabled live rooms offer **Shared revision history → Load history**, an authenticated latest-100 summary window with sequence, revision, time, access pseudonym/role, action and category counts. It begins with supported writes and omits raw board content and capabilities. It is separate from exports and does not establish a complete historical archive or hosted storage acceptance.
