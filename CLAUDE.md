# Claude project guidance

Follow `AGENTS.md` as the shared product and safety contract. Use [docs/AGENT_WORKFLOWS.md](docs/AGENT_WORKFLOWS.md) for the full human/agent handoff and [docs/RESEARCH_PLAYBOOK.md](docs/RESEARCH_PLAYBOOK.md) for evidence standards.

For a new trip, ask one compact high-impact batch, state assumptions, and build three or more materially different route candidates *before* price research. After representative cash/points, direct/connection, open-jaw/positioning, rail, and car comparisons exist, ask only questions that resolve an observed tradeoff. Do not optimize away a stated preference, a rejection, or a locked item without explicit review.

Keep edits in normalized trip data; do not regenerate a monolithic personalized HTML file as the source of truth. Build broad, source-backed city catalogues before narrowing to a clustered, feasible day plan. Mark research with source, checked-at time, fact/estimate/quote status, and uncertainty.

MCP servers and Gmail are optional user-local integrations. Never write real tokens into this repository or assume that a named travel service has an official MCP server. Confirm provider access and use credential-free configuration examples. Gmail/email/file imports are read-only, minimum-scope, explicitly approved candidates: deduplicate, redact, show proposed normalized records, and wait for approval before import or any booking-state change. Never export or commit secrets, email links, confirmation codes, references, loyalty identifiers, or raw private content.

Use [the complete setup and trip-planning prompt](prompts/START_HERE.md), then [prompts/SETUP_GUIDE.md](prompts/SETUP_GUIDE.md) and [prompts/NEW_TRIP_GUIDE.md](prompts/NEW_TRIP_GUIDE.md). Keep a date/airport/program/mode coverage ledger, compare hotel bases and all-in stay value, research each city broadly, and disclose unsearched combinations and booking gaps. Keep modules optional and user-owned: manual planning first, research credentials only when useful, and Vercel or self-hosting only after deployment authorization. Check current plan eligibility and permitted uses; never imply that a personal key licenses a shared public service.

For arbitrary destinations or dates, use `/plan` or `trip:init` and validation. Accepted `/plan` records open a separate manual workspace with routes, explicit coordinate maps, timed day activities and previewed booking records. Device saving/resume is explicit and isolated by trip. Research coverage and sourced cash/award/stay/transport comparisons retain unknowns; they do not acquire live inventory. Optional account save/load is explicit and separate from browser storage. The sample atlas and its update bundles retain their specialized scope. See [current capabilities](docs/IMPLEMENTATION_STATUS.md) and [export formats](docs/EXPORTS.md).

Optional `/collaborate` is a separate live activity/day board. Generic plans can prepare share-safe board JSON for preview/import before room creation. Owners manage dates/cities, expiring invitations, owner-link replacement and deletion; editors edit activities/days; viewers read. Reconciliation requires explicit choices against a current revision. Consent-based browser recovery excludes capabilities and unfinished forms. Configure user-owned durable SQLite/Postgres and private creation code where required; no provisioning, sending or deployment follows automatically. Optional Better Auth accounts separately store encrypted, tenant-isolated planning workspaces with revision checks, a 20-plan limit and password-confirmed deletion. Recovery email remains an unwired external adapter. [Live rooms](docs/LIVE_COLLABORATION.md) · [Private accounts](docs/PRIVATE_ACCOUNTS.md).

Use the [feature implementation ledger](docs/BUILD_PROGRESS.md) to distinguish shipped slices from remaining work. Generic tools include explicit dated allocations, source receipts that become review-required after record changes, selected-quote partial budgets, device-library recovery and complete JSON preview/import. The detailed arbitrary-trip city/day view supports activity/day/city edits and attributed photos/pins; specialized hotel/transport/route parity is pending. Reviewed board imports exclude bookings and require per-change choices and explicit timing for new activities. Scenarios create a new identity under a reviewed booking-copy policy; named device snapshots require a readable restore preview and explicit current-copy disposition. Optional presence represents access links, not people; bounded live notices preserve dirty drafts and polling fallback. The cash matrix requires an explicit run and records bounded exact-query coverage only. Pending board proposals support owner review plus access-pseudonymous votes/comments; these do not identify a person or create notifications.

Before closing, use [the acceptance checklist](docs/AGENT_WORKFLOWS.md#acceptance-checklist). Report the actual data surface, verified actions, authorized tools, coverage omissions and remaining decisions. Setup requires a working tested path, not only environment names; a planning handoff requires comparable evidence and schema validation, not only prose. Preserve unrelated working-tree changes, and use synthetic/sample records for checks and screenshots. Follow the installed Next.js documentation before framework changes.
