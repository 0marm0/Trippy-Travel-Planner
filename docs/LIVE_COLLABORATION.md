# Live collaboration

Manual planning and the reviewed public sample work without collaboration configuration or provider accounts. Live collaboration publishes only the reviewed planning board: trip title and dates, cities, activity catalogue, activity assignments to days, and optional bounded share-safe activity/day/route/stay suggestions and accepted route/stay planning ideas for owner review. It does not share booking records, booking states, prices, raw email, private trip DTOs, or provider credentials.

## Run on one persistent local server

Use Node 22.18+ or Node 24. Set `COLLABORATION_ENABLED=true` in untracked `.env.local`, then run the app. The Node server persists rooms and hashed access capabilities in ignored `.private/collaboration/rooms.sqlite`. Keep that directory on persistent storage and include it in your private backup process. `COLLABORATION_SQLITE_PATH` may select another database file inside that directory. A restarted server using the same database retains rooms, revisions, and revoked invitations.

SQLite mode serves several browsers connected to that same server. It is intended for one server with a persistent disk, not horizontally scaled instances or ephemeral serverless filesystems. Vercel, AWS Lambda, and Google Functions fail closed in local SQLite mode. Room API responses are private and never cached.

For remote browser access or any production server, configure `COLLABORATION_CREATE_CODE` in the untracked server environment: a privately generated value of 16–256 characters without whitespace. The room creator enters it in a masked field; the browser sends it only as `X-Trippy-Create-Code`. Do not put the value in a link, trip record, screenshot, or tracked file. A remote or production host without a valid configured code denies room creation; existing capability-based rooms remain accessible. Only development/test loopback creation can omit the code when none is configured. Production requires it even if an incoming Host claims localhost. Status reports only whether a code is required and creation is available. Production SQLite paths reject symbolic-link directories/files and verify that storage resolves inside the private collaboration directory.

Origin checks use the validated incoming `Host` authority rather than Next's internal request hostname, so a browser opening `127.0.0.1` is not rejected when Next internally uses `localhost`. Foreign browser origins and cross-site fetch metadata remain blocked. An HTTPS reverse proxy must preserve the public Host. If it terminates TLS before a plain-HTTP Node server, set `COLLABORATION_TRUST_PROXY=true` only when that trusted proxy overwrites `X-Forwarded-Proto` with exactly `https` or `http` and direct untrusted ingress cannot supply it. Vercel's managed ingress supplies that scheme. Forwarded Host and multi-value scheme chains are never trusted.

## User-owned hosted storage

For multiple application instances or a serverless host, configure a user-owned Postgres database using `COLLABORATION_DATABASE_URL` alongside `COLLABORATION_ENABLED=true`. The app creates namespaced tables for rooms, hashed capabilities and short-lived presence leases. Configure TLS through your database provider's supported connection settings; the app does not disable certificate verification. The database account must have permission to create these tables and read/write them. Database hosting, billing, backups, network controls, and deployment are the operator's responsibility. Implementation does not provision a service or deploy the app.

The Postgres adapter uses transactions, row locks, and conditional updates, with bounded connection, statement, and idle-transaction timeouts. SQLite uses immediate write transactions and serializes transactions inside the running server. Postgres integration requires a configured database; local automated tests exercise SQLite, including restart durability. No hosted database was provisioned or contacted for these tests.

## Share and access

The owner reviews the share-safe board before creating a room. Invitation capabilities grant editor or viewer access; they do not establish a person's identity. Anyone possessing a capability has its role, so share links only with intended recipients. Links carry capabilities in the URL fragment and the browser sends them in the Authorization header, never in query parameters or trip records. The server stores SHA-256 hashes, not plaintext capabilities. Room identifiers alone do not grant access. No email is collected and invitations are not sent automatically.

Owners change the trip frame, create expiring editor/viewer invitations, revoke them, replace owner access and delete rooms. New invitations default to seven days and permit a chosen expiry within 30 days; legacy invitations without an expiry remain valid until revoked. Expiry/revocation is checked during reads and inside write transactions. Editors change activities and day assignments. Viewers read the board. Only owners can list the persisted invitation identifiers and roles; the original invitation token is returned once and cannot be recovered from its hash. Keep the owner capability privately: losing it means losing owner access. Replacing the owner link revokes old owner access and returns the new capability once, while existing editor/viewer invitations retain their roles. Rotation and deletion require the observed revision and an explicit review/approval. An interrupted response can have an unknown outcome; do not blindly retry rotation. Deletion removes the room and all its stored capabilities; subsequent access fails, while already-viewed/local/exported copies cannot be erased. Revocation denies subsequent reads and writes; it cannot erase a copy someone already saw.

There is no public room directory, account login, booking action, calendar action, or export endpoint. Capability access is separate from the existing local trip planner's data and permissions. The public sample endpoint explicitly calls `loadCurrentTrip({ allowPrivate: false })` and projects only catalogue fields and reviewed day assignments to known retained activities; it never uses the private-data gate. Metadata reports retained catalogue items, scheduled activities/days, and omitted catalogue items. Duplicate or unavailable activity assignments are omitted.

## Board-first planning and reviewed suggestions

The main workspace prioritizes the day board and activity catalogue; trip creation/import and sharing settings remain available without occupying the main planning surface. Activity forms use a detail drawer, catalogue search/city filters keep the list usable, and a focused day retains assignment controls.

Owners and editors can append an activity proposal, a proposed day move, or a share-safe route/stay idea to their draft, then explicitly save it to the room. Submission creates a `pending` suggestion and does not apply that proposal to the catalogue/day board. A viewer cannot submit or review. Existing editor permission to edit activities/days directly remains available; suggestions are an optional review path, not an editor approval gate.

Only the owner applies or rejects a saved pending suggestion, after inspecting it and resolving/saving unfinished local changes. [`suggestions.ts`](../src/lib/collaboration/suggestions.ts) derives only the proposed activity/day change or appends the reviewed route/stay planning idea. [`store.ts`](../src/lib/collaboration/store.ts) performs review inside the same room transaction as role/access validation, observed-revision checks and the conditional write. Stale, revoked, expired or deleted-room access cannot apply a proposal; uncertain outcomes require a reload rather than a blind retry. General board writes may append pending suggestions but cannot rewrite or remove existing pending/applied/rejected receipts or accepted route/stay ideas. Applied and rejected records remain separate from the active board.

Route/stay ideas use a separate allowlisted shape: safe title/notes, existing city reference for a stay, or distinct origin/destination city references and an explicit mode/unknown for a route. No booking/status/price/source-link/private-identifier fields are allowed. Applying a proposal appends it to the optional `planningIdeas` array (maximum 100); it never creates or modifies a booking, selects a private workspace route/stay or establishes dates, cost, schedules, inventory or availability. Full capacity rejects review without a partial write. These accepted ideas survive validated board JSON/recovery and latest-first room reconciliation; they are excluded from owner-workspace import. Unfinished idea forms stay in the tab, block save/review/reconciliation, and are excluded from recovery/downloads. Confirmed board replacement clears them; ordinary refresh preserves them.

The optional `suggestions` array is capped at 100 records including resolved receipts, with privacy/reference checks on proposed content and dates. Legacy boards without suggestions or planning ideas remain valid. Suggestions participate in entity-level reconciliation, so independent local/latest additions are preserved for explicit choices. Suggestion receipts do not establish a verified author identity; discussion uses the separate access pseudonyms below. This is not a full audit log. Relevant implementation: [`schema.ts`](../src/lib/collaboration/schema.ts), [`reconciliation.ts`](../src/lib/collaboration/reconciliation.ts), [`collaboration-workspace.tsx`](../src/components/collaboration-workspace.tsx).

## Proposal choices and comments

A saved pending proposal can receive `support`, `concern` or `neutral` from an owner/editor access capability. A second choice from the same capability replaces only that capability's current choice for the same proposal. It cannot replace another invitation's choice. Choices do not apply a proposal or alter the board; the owner still explicitly reviews application/rejection.

Attribution is a server-derived public pseudonym (`access-` plus the resolved capability-row identifier) and its owner/editor role, **not a verified person's identity**. Anyone sharing the same invitation shares that choice identity. A new invitation or replaced owner access has a different identity; old discussion remains attributed to its historical access. Capabilities, their hashes, email addresses and provider identities are never stored in the board. Clients cannot supply an actor or role in the interaction endpoint. The server checks access, expiry/revocation, pending-proposal status and the observed room revision inside the same write transaction.

Comments attach only to proposal IDs, use at most 500 share-safe characters, and receive a server record ID, timestamp and access attribution. Owner/editor access may append them; viewers may read. Posted comments cannot be edited or individually deleted through general board writes. Discussion remains readable after the proposal is resolved and is removed with room deletion; existing device/downloaded copies cannot be recalled. There are at most 200 comments and 1,000 current vote records per room, and interaction writes reject state exceeding 512 KiB. This is bounded proposal discussion. The separate revision-summary history below tracks supported server mutations; it is not an activity chat or personal must-do list. The separate opt-in presence service below never stores discussion text.

The optional `interactions` object keeps legacy boards compatible. General PATCH must preserve its history exactly and cannot forge a server attribution, change votes or drop old comments. New-room creation rejects nonempty imported interaction history instead of transferring purported authorship into another room. Reconciliation always carries the latest server interactions and never presents them as client-overwrite choices; ordinary board/proposal conflicts still require review.

The discussion drawer preserves unfinished comment text in the current tab when closed or when a stale request fails. Opening another discussion requires discarding an existing different-proposal draft. Posting requires a connected role, pending proposal and resolved/saved board changes. An uncertain network outcome pauses writes and requires a current-room reload before retrying; no blind repost is performed. Unfinished comment text is excluded from device recovery and board JSON. No email, invitation, webhook or push notification is sent.

## Opt-in access presence and faster updates

Connected owners, editors and viewers can read a compact active-access strip. Reading does not announce the reader. **Show this access as active** explicitly starts a lease lasting at most 30 seconds; this tab renews it approximately every 12 seconds while connected. The strip represents capability pseudonyms and roles, not verified people or a traveler count. Tabs sharing an invitation share one lease; either tab can renew or withdraw it. Access changes reset the opt-in controls.

Presence stores only a room ID, resolved capability-row ID and lease expiry in the same SQLite/Postgres database. It does not store draft text, email, IP addresses or personal names. Expired leases are excluded immediately and cleaned on subsequent presence operations; database files and private backups can retain prior bytes. Live nonrevoked/nonexpired access is checked inside the room transaction, and summaries join only active capabilities. Revocation and owner rotation remove affected leases; deleting a room removes all its leases. Presence updates do not change the board revision, export state or proposal history. Closing or disabling presence makes one best-effort withdrawal; a missed request expires within 30 seconds. Background-tab throttling can make a lease lapse.

**Use faster live revision notices** separately opts into authenticated fetch-based server-sent events. Authorization stays in headers. Each connection lasts at most 25 seconds and performs at most 25 summary checks, approximately one second apart; only revision and presence summaries are streamed. Access is rechecked for every summary. Revoked/deleted access closes the stream, and tab/access changes abort readers and reconnect timers. The client bounds each transport attempt to 30 seconds and reconnects after four seconds. Proxies may buffer or disable streaming; the existing four-second room polling remains active throughout.

A revision notice invokes the existing guarded room refresh. Unsaved board edits, unfinished activity/route/stay forms and discussion drafts cause a latest-version review instead of replacement. Busy operations and access generations retain their existing checks. These are bounded revision notices, not push notifications, guaranteed latency, collaborative cursors or automatic merging. Synthetic SQLite/store/route tests cover expiry, cross-connection leases, revocation, owner rotation, room deletion, authorization, cancellation and reconnect. Hosted Postgres and proxy behavior require separately authorized acceptance. Evidence: [`presence.ts`](../src/lib/collaboration/presence.ts), [`events.ts`](../src/lib/collaboration/events.ts), [`collaboration-presence.tsx`](../src/components/collaboration-presence.tsx), [`collaboration-presence.test.mjs`](../tests/collaboration-presence.test.mjs), [`collaboration-presence-routes.test.mjs`](../tests/collaboration-presence-routes.test.mjs).

## Conflicts and privacy

Every write requires the last observed revision through `If-Match`. A stale write returns HTTP 412 and the latest safe state. The UI preserves its board and unfinished planning forms; saves pause until explicit review. Reconciliation compares original, local and latest states by field/entity and ordered day assignments. Conflicts require choices; compatible independent edits have editable suggestions. Another revision or local change invalidates the review. Final validation rejects deleted references, duplicate assignments and out-of-range dates, then the owner/editor explicitly saves the chosen draft. There is no unconditional overwrite or automatic retry.

With consent, device recovery stores only a validated board plus its base/revision under a room-specific key. Reload offers review before restoration; disabling retention removes the copy. Access capabilities stay in the separate session flow, and unfinished forms/import text/creation codes are excluded. Other users of the same browser may see retained boards. Header-link/unload warnings help preserve edits but are not a guarantee for every browser-history navigation.

Validated board JSON can be downloaded and previewed/imported by an owner or in a local board before sharing. Generic-to-board projection includes cities, manual city coordinates, activities and day assignments. Bookings, research, account identities and capabilities never transfer. Creating/publishing a room remains separate from importing a file.

In `/plan` → **Plan together**, download a base snapshot before group editing. In `/collaborate` → **Draft recovery & board JSON**, download the edited validated board. Back in the owner workspace, paste the original base envelope and edited board to preview three-way city/activity/day changes against the current local workspace. Every compared field requires an explicit local/group choice; conflicting additions, edits and deletions remain visible. A workspace change invalidates acceptance until a fresh preview. Trip dates and destination IDs must match; cities are never silently mapped by name.

Existing clock times and activity metadata remain local. New/unscheduled group ideas need explicit day/time/duration choices. Ordered board days do not set clock times or replace owner day-destination allocations. Board-only photos, source links and activity coordinates are disclosed as unsupported imports. Pending proposals, accepted route/stay ideas, votes/comments and access metadata are excluded. Only applied city/activity/day edits enter this import review; accepting a route/stay idea does not make it an importable booking or route. Booking records/details, research, quotes and account data are conserved. Changed supported records retain their evidence with `reviewRequired`; deleting an activity with a receipt is blocked until reviewed manually. City renames can be blocked by existing research/quote/route identity checks, preserving those records instead of rebinding them. Applying changes uses the owner workspace's existing explicit device-save preference; snapshots/scenarios have their own separate save decisions. File handoff establishes no ongoing synchronization or automatic room fetch/write. Evidence: [`reviewed-collaboration-sync.ts`](../src/lib/reviewed-collaboration-sync.ts), [`reviewed-board-sync.tsx`](../src/components/reviewed-board-sync.tsx), [`reviewed-collaboration-sync.test.mjs`](../tests/reviewed-collaboration-sync.test.mjs).

The schema bounds strings, cities, activities, day assignments, dates, and request size; checks referential integrity; rejects unsupported fields; and blocks common personal identifiers, email addresses, mail links, credentials, and booking-reference labels. Activity images permit only local reviewed media paths. Attributable source links permit HTTPS without userinfo, query parameters, or fragments. These checks cannot recognize every private fact expressed in prose. Review all notes and titles before publishing and never enter confirmation codes, traveler email addresses, seats, loyalty details, or secrets into the collaboration board.

This implementation offers polling, persistent room state, explicit reconciliation, consent-based local recovery, expiring/revocable invitations and reviewed owner rotation/deletion. It includes optional capability presence and bounded live notices, but has no owner-capability recovery, automatic merge, full-content/unlimited audit history, end-to-end encryption or automatic room expiry. Optional private accounts are a separate module; they do not recover a lost room capability. See [private accounts](PRIVATE_ACCOUNTS.md). A public internet operator should supply request throttling and storage retention controls appropriate to the deployment; the app does not pretend the capability model is an enterprise identity system.

## API

All room requests use `Authorization: Bearer <capability>`, apart from room creation. JSON bodies reject unknown fields. Mutations reject cross-origin browser requests. No route accepts capability query parameters.

| Method and path | Request | Result |
| --- | --- | --- |
| `GET /api/collaboration/status` | none | Safe configured mode, explanatory message, `creationCodeRequired`, `creationAvailable` |
| `GET /api/collaboration/sample` | none | `{ state, metadata }` from the reviewed public sample |
| `POST /api/collaboration/rooms` | `{ state }`, creation-code header when required | `{ roomId, ownerToken, revision, state }` |
| `GET /api/collaboration/rooms/[id]` | capability | `{ roomId, role, revision, state }`; owners also receive invitation inventory |
| `GET /api/collaboration/rooms/[id]/presence` | Any active room capability | Revision and active capability pseudonym/role summary; does not announce the reader |
| `POST /api/collaboration/rooms/[id]/presence` | Any active room capability, `{ present: boolean }` | Explicit 30-second lease renewal or withdrawal; no board revision change |
| `GET /api/collaboration/rooms/[id]/events` | Any active room capability, Authorization header | At most 25 seconds/25 summary checks of revision/presence SSE; access rechecked, no board payload |
| `PATCH /api/collaboration/rooms/[id]` | capability, `If-Match`, `{ state }` | Updated revision, or 412 with latest safe snapshot |
| `POST /api/collaboration/rooms/[id]/suggestions/review` | Owner capability, `If-Match`, `{ suggestionId, decision: "apply" \| "reject" }` | Updated revision/state; only a pending proposal can be reviewed, stale review returns 412 |
| `POST /api/collaboration/rooms/[id]/suggestions/interact` | Owner/editor capability, `If-Match`, `{ suggestionId, action: "vote" \| "comment", value }` | Current-revision vote replacement or safe comment append on a pending proposal; actor/time are server-derived, viewers denied, stale state returns 412 |
| `POST /api/collaboration/rooms/[id]/invites` | owner capability, `{ role: "editor" \| "viewer", expiresAt?: ISO UTC }` | `{ inviteId, token, role, expiresAt }` |
| `DELETE /api/collaboration/rooms/[id]/invites/[inviteId]` | owner capability | `{ revoked: true }` |
| `POST /api/collaboration/rooms/[id]/owner-token` | Owner capability, `If-Match`, `{}` | New one-time owner token and incremented revision; old owner denied |
| `DELETE /api/collaboration/rooms/[id]` | Owner capability, `If-Match` | Deletes room/capabilities; stale access denied |

Hosted Postgres remains untested against a user-owned database.

## Shared revision history

Inside a connected room, open **Shared revision history** and select **Load history** or **Refresh history**. Owner, editor and viewer access can read the latest 100 retained summaries; loading is explicit and does not add background polling. Each summary has an order, board revision, server time, action, pseudonymous access alias/role and fixed category counts. Access aliases identify capabilities, not verified people. Access-management events can share the current board revision; sequence gives their order.

History starts with writes supported by this version. Existing rooms have no fabricated past. It is a bounded summary window rather than a full-content archive: activity names, notes, comment text, raw record IDs, board snapshots and invitation values are excluded. History is not part of activity-board JSON, workspace exports or client write requests. Room deletion removes its server history too.

Successful board edits, proposal interaction/review and invitation/revocation/owner-rotation changes append in their mutation transaction. Failed, stale or unauthorized writes do not append. Reads require the Authorization capability and recheck expiration/revocation inside the locked transaction. SQLite synthetic tests cover these contracts; hosted Postgres operational acceptance is separate.

`tests/collaboration-planning-ideas.test.mjs` covers legacy optional-field compatibility, private/unsupported fields, broken city references, owner-only route/stay review, immutable accepted ideas, stale revisions/expired access, interaction retention, SQLite restart durability, JSON/recovery/reconciliation preservation and capacity rollback. These are bounded synthetic/local contracts; integrated browser checks, hosted Postgres and independent release/accessibility acceptance remain separate receipts.
